# 002 授权

授权决定谁可以启动工作，以及这些工作可以包含什么。本文建立在 [001 领域模型](001-domain-zh.md) 之上。

许可名单、规则与授权由宿主强制执行。消息、评论和被引用的文档都只是决定的输入；它们无法改变这些权限。

## 触发的两条路径

### 评估：判断是否启动工作

来源会记录一条消息是否指向智能体：`mention` 表示提及机器人或智能体账号，`direct` 表示私信。准入层会检查发送者与该来源的策略：

- 在许可名单上的人若指向智能体，即构成一次明确请求。
- 人对已有工单的线程的后续发言，遵循下文规则。
- 其他人类消息按其"接收范围"套用准入表。
- 来源机器人名单上的机器人可以产生推断候选，但永远不能产生明确请求。其他机器人一律不予准入。

### 订阅：延续既有工作

已订阅线程上的每条消息都会作为上下文抵达其订阅的工单，包括来自机器人和 CI 的消息。这种投递绕过准入层，也不授予任何新权限。每个工单仍受其授权约束。

人在工单自己的线程上发的消息，归该工单的执行器判断。主 Session 把某条消息挂到某个工单上时，同样如此。当执行器拥有该消息时，它不进入评估，也不会产生决定。每个执行器要么在工单范围内处理该请求，要么把它交还回去，以便路由到别处。

只要工单是活跃的，归属关系就一直存在，即使有人移除了它的订阅。归属关系也覆盖这样一种已结束工单：它并非被人停止，且有消息正等着恢复它。

主 Session 会收到一条"后续发言"通知。当执行器拥有该消息时，主 Session 只能按当事人的请求停止工作；接单、挂载、忽略和重新排队都会被拒绝。停止操作仍需通过准入层，并使用下文所述的后续发言强度。

### 交还与释放后续发言

当执行器认为某项请求超出工单范围，或属于另一个工单时，它会交还该消息一次。工单保留它的订阅。如果被挂载的线程与工单无关，执行器会交还它在该线程上拥有的消息。

只有当没有任何工单仍拥有某条消息时，它才会进入一次新的评估。它的候选会包含各执行器给出的理由。准入层会把它当作该线程上的一条普通消息来判断，主 Session 可以接单、挂到别处，或忽略。交还一条工单本就不拥有的消息（例如机器人消息，或人已经送去评估的消息）不会排入任何队列。

工单结束时，它会释放执行器尚未读取或尚未接手的后续发言。这包括从未投递给执行器的消息，以及在最后一次报告或回合结束之后才投递的消息——前提是执行器既没有确认、也没有回复、也没有交还。被释放的消息，若没有其他工单拥有它，就进入评估。一次停止只结束被停止那个工单的工作。

已停止的工单不会把它的停止消息再次送去评估，除非有另一个工单把它交还回来。执行停止的主 Session 可以把该消息的其余部分作为新工作接单。

人可以从面板把一条已被拥有的后续发言送去评估。如果主 Session 随后又把它挂回某个活跃工单，执行器会再次收到它。当没有任何有效判断覆盖该消息时，面板也会提供"重新评估"。

### 仅作上下文的订阅

执行器可以为获取上下文而跟随一个相关线程，例如另一个 Issue 或 pull request。该线程上的消息会抵达工单，但不授予权限，也不带来后续发言强度。除非主 Session 从该线程挂载了某条消息，否则那里的人类消息不会恢复已结束的工单。主 Session 关于其他工作的说明同样只是上下文。

未能抵达任何工单的人类消息——包括那些工单已被人停止的线程——走评估路径。机器人消息独立于它们向已订阅工单的投递，同样走这条路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit 明确 | 名单上的人指向智能体，或在已有工单的线程上继续发言；准入表中被设为"明确请求"的单元格 |
| inferred 推断 | 不在名单上的人在已有工单的线程上继续发言（除非其单元格设为明确）；准入表中被设为"推断候选"的单元格；来源机器人名单上的机器人发来的消息，且该消息指向智能体，或出现在来源接收全部消息的地方 |
| not admitted 不予准入 | 其他任何机器人的消息、准入表忽略的一切，以及接受模式为 `off` 时的所有推断情形 |

对于不在名单上的人，"明确"单元格优先，即使在已有工单的线程上也是如此，并且在任何接受模式下都生效。否则他们的后续发言属于推断，在 `off` 模式下不予准入。仅在上下文线程上的消息套用准入表，而不使用后续发言强度。

## 准入

每个来源的策略里有一张准入表。它的行是"接收范围"：

- **飞书：** 每个已配置的群、机器人从中收到 @ 的其他群，以及私信。只有在飞书卡片上将 **其他群** 设为 **仅 @** 时，才会接收其他群。
- **GitHub：** 新 Issue、新 pull request、评论，以及默认分支的 CI。

一行最多有三个单元格。每个单元格决定一条消息是成为明确请求、推断候选，还是什么都不成为：

| 单元格 | 可选值 | 默认 |
| --- | --- | --- |
| 在名单上，未指向智能体 | inferred、ignore | inferred |
| 不在名单上，指向智能体 | explicit、inferred、ignore | ignore |
| 不在名单上，未指向智能体 | inferred、ignore | ignore |

"未指向"类单元格只在来源能收到全部消息时才可用，例如设为 **全部消息** 的飞书群，或开启了"接收全部"开关的 GitHub 范围。CI 结果没有发送者，因此它的行只提供最后一个单元格。机器人消息使用机器人名单判断，而不是这些单元格。

把"不在名单但指向智能体"的单元格设为 explicit，就能让该范围内任何人通过 @ 智能体来请求工作。这对专门的答疑群很有用。推断候选仍取决于接受模式。后续发言通常绕过这张表，但"明确"单元格仍然会授予明确强度。

准入表是策略版本的一部分。削弱某个单元格，不会立刻停掉依据它接单的、仍在开启的工单。当这些工单在恢复前被重新校验时，可能会被撤销授权。

### 机器人与自动评审者

宿主会把 GitHub App、以 `[bot]` 结尾的登录名，以及飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 这样的机器人，它们发来的消息可以成为推断候选。它们必须指向智能体，或发在接收全部消息的范围内。它们不能发出明确请求，也不能停止工单。

使用普通账号的自动评审者，在宿主看来仍算作"人"。它的评论会抵达已订阅的工单，并产生后续发言通知。团队提示词文本必须把这类账号标记为自动评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接单、挂载、停止或忽略决定。每个条目独立处理：某项被拒绝或某个字段缺失，不会阻止其余条目执行。

推断候选通常需要一次完整的研判。只有一种捷径：如果它的卡片明显不涉及任何已启用的规则，例如纯聊天或无关讨论，主 Session 可以直接忽略它。决定中会记录 `ignoredFromCard`，以便与"经规则研判"区分开。主 Session 会在其策略提示词段落中读取已启用的规则。

接受推断候选始终需要研判。直接接单会拒绝那些准入层未判为明确的触发。

## 接受模式与规则

接受模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断都不会成为候选，例如未指向智能体的消息、机器人的消息，或名单外人士的后续发言 |
| `observe`（默认） | 会对推断候选做研判；研判结论为正时，记录为标记"本会接单"的忽略，且不真正接单 |
| `auto` | 对推断候选的正向研判会直接接单 |

明确请求在任何模式下都有效。先从 `observe` 开始，审阅记录下来的决定之后，再切换到 `auto`。每次研判会对每条已启用规则各判断恰好一次，无论是否命中。主动接单要求至少命中一条规则。

每条规则描述一类主动型工作。工单的授权会记录命中的规则，其执行器会收到这些规则的名称与说明。

对该工单而言，规则中关于流程与沟通的要求会覆盖默认值。一条"静默"规则可以抑制确认回复；一条"评审"规则可以指定合并前必须的评审人与批准。适用于所有工单的要求，则应写在团队提示词段落里。

## 策略版本

规则、接受模式以及每个来源的策略部分共同构成策略版本。每个授权都记录它被接受时所处的版本。

版本变更会废弃正在运行的评估，并把它们的触发重新排队。它还会向每个受影响且活跃的工单发送一条"策略已变更"输入。该输入会说明以下哪种情况：

- 命中的某条规则发生了变化（包括它的新文本），或已不再适用；
- 请求者已不再有权发起工作；或
- 主动型工作已不再被接受，例如模式已不再是 `auto`。

未受影响的工单不会收到通知。变更不会立刻撤销活跃工单的授权。

来源配置与策略是分开的。它控制什么进入系统：读哪些群，以及某个范围是接收全部消息还是仅接收 @。授权会记录其来源和接收范围。恢复要求来源仍然监听该线程，但不要求它仍然接收那里的全部消息。

当来源关闭时，回复会等待。如果来源已不再监听其目标地址，回复会被丢弃。

针对"执行器可以如何处置自己结果"的条件，例如何时可以合并，并不决定谁有权授权工作。它属于智能体的指令，而不属于策略。

## 恢复与停止

已结束的工单保留它的授权。人在它自己的某个线程上发消息，就能在无需新的评估或决定的情况下恢复同一项工作，不论发送者是谁。机器人和 CI 不会唤醒已结束的工单。执行器判断该请求是否符合范围，不符合就结束这一轮。

只有三种操作会改变授权：接单创建它、人发出的停止收回它、重新校验失败撤销它。被人停止的工单保持结束状态，不再接收任何内容。在那里请求工作，需要一次新的接单。

### 恢复前的重新校验

来源必须仍然监听原来的线程。其余检查取决于授权的依据：

- 明确后续发言产生的授权直接通过。
- 推断产生的授权需要 `auto` 模式，且其命中的规则仍然启用。
- 由准入表单元格准入的授权，在当前的表和发送者归属下，必须至少仍能获得其原有强度。因此，把某个发送者从名单中移除，可能撤销通过"名单内发送者"单元格获得的授权。
- 机器人产生的授权要求该机器人仍在来源的机器人名单上。推断产生的表格授权与机器人授权，还需要 `auto` 模式和已命中规则处于启用状态。
- 其他授权要求发送者仍在来源的许可名单上。

如果重新校验失败，工单保持结束，也不接收任何等待中的消息。每条消息都被视为未抵达任何工单；如果没有其他工单拥有它，它就进入评估。主 Session 不会被告知它抵达过某个执行器。处理暂停之后也遵循同样规则。向该工单挂载会被拒绝，继续工作则需要一次新的接单。

- **人在线程里说"停"是一个普通触发，** 由评估来决定停止。执行器不能自行宣称有人要求它停止。
- **面板里的"停止"是一条命令。** 它直接作用于工单，并被记录为人工停止。
- **等待类条件属于来源。** 诸如"N 小时无人认领"这样的条件，会是一个自行等待并再次检查的来源；评估永不等待。

## 评估未能完成时

时限从候选抵达主 Session 时开始计算。等待投递所耗的时间不计入，未投递的候选永不过期。

超时的评估会把它的触发重新排队，另做一次尝试。连续两次重试之后，第三次超时会记录 `unavailable`。研判失败同样记录 `unavailable`；之后到来的触发可以启动一次新的评估。策略变更，或基于过期策略做出的决定，会记录 `unavailable`，并立刻以当前版本重新排队该批次。

`evals` 健康项会报告最近一小时内未解决的 `unavailable` 决定。`scripts/dsh-superagent status` 的输出中也包含该错误。

只有当 `unavailable` 决定距今不足 24 小时、仍是其线程上最新的决定、尚未被忽略，且该线程既未排队也不在评估中时，面板才会请求人工介入。人可以重新评估该触发，或忽略这个问题。
