# 000 设计理念

dsh-superagent 是一套框架，也是一种与智能体协作的工作方式。它的核心原则是：

**尽可能少占用人的注意力，尽可能多地交付价值。**

项目中的每一部分，都要用它消耗的注意力来衡量。一条消息、一次通知、一个问题、一项设置、一个面板元素、一段文档，各自都要消耗某个人的注意力，因此每一处都必须带来超过这份消耗的价值，否则就应当删掉。

## 对智能体的要求

- **只在被请求时行动，或在成文规则允许时行动。** 只有当请求直接指向智能体、且来自团队许可的人时，才算作一次请求：此人要么在许可名单上，要么处于团队开放了请求权限的对话中。没人请求的工作，需要团队写下的规则来授权，并且启动时只进入"记录"模式——只记下智能体本来会做什么，而不真正执行。
- **只在有人必须行动、或某个结果对人有用时开口。** 它只确认一次请求，并说明自己将要做什么。工作过程中保持安静。直到结果就绪、需要决策、或无法完成时，才再次发言。消息要短，并发送到提出请求的那个对话里。
- **一次只问一个具体问题**，以结构化表单的形式提出，让问题真正抵达当事人，而不是陷在一份长报告里。
- **以影响范围决定何时停下，而不是以投入多少。** 局部改动推进到可评审的结果为止。需要设计决策的改动，则带着一个明确的问题停下来。
- **如实汇报。** 草稿要标明尚未完成，失败就报告为失败，绝不为了回避提问而绕过某个限制。

## 对设计的要求

- **概念要少。** 设计中只有领域概念（例如来源），以及它们的具体实现（例如 GitHub 和飞书）。业务需求要么成为其中某个概念的一个属性，要么成为智能体遵循的一段提示词。设计不为此新增概念。
- **设置要少。** 当某一个取值适用于几乎所有团队时，就用默认值取代设置项。团队用文字描述的行为，属于提示词文本，不是设置项。
- **面板只展示需要人来处理的事项。** 它优先列出等待人处理的内容。健康状态下不占任何空间。
- **文档要按顺序阅读。** 每篇编号文档只建立在它之前的那些文档之上，因此读者永远不会遇到尚未引入的概念。

## 责任

智能体会以你团队日常可见的账号发表评论、提交 pull request、给人们发消息。它发出的每条消息都在消耗同事的注意力，而这由你负责。智能体能做的事越多，运营者对团队负有的谨慎义务就越大：

- **从窄处开始。** 一开始使用一份简短的许可名单，并让主动型工作只做记录。等"智能体本来会做什么"看起来正确之后，再放宽这两者。
- **为更少的噪音而调优。** 当智能体太吵时，把它的提示词改得更短、更严格，或者暂停它。不要为了解释噪音而增加更多消息。
- **不要用它来堆量。** 大批量 pull request、广播式消息和无效忙碌，给团队带来的成本大于收益。
- **为你名下说出的话负责。** 读一读智能体以你的名义发布的内容，发现错误就回到提示词里去改正。

目标是：在对的时候提供对的帮助，其他任何时候都不打扰。
