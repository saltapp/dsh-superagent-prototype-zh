# 003 执行

本文沿着一个已接单的工单，走过执行、投递与恢复的全过程。它建立在 [001 领域模型](001-domain-zh.md) 与 [002 授权](002-authorization-zh.md) 之上。

## 工单阶段

每个开启中的工单都只有一个阶段，由它此刻在等待什么决定。请从上往下读这张表，第一个匹配的行即为结果。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；2 秒后重试，之后延迟翻倍直至一分钟；一次成功、一个新的派工，或工单结束，都会清除该状态 | 输入未送达 |
| person / answer | 存在一条待人工决定 | 等待回答 |
| person / review | 最新报告为 `ready` | 等待评审 |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，且此后没有人的消息抵达该工单 | 受阻 · 失败 |
| working / queued | 没有派工，或派工处于待启动 | 已排队 |
| idle | 最新报告为 `waiting`，或派工已结束 | 等待触发 |
| working | 其余所有情况 | 执行中 |

`person` 类阶段意味着：没有人的输入，工单就无法继续。一条新的人类消息会把 `blocked` 或 `failed` 的工单释放给它的执行器，于是它转入下一个匹配的阶段，通常是 `working`。

`idle` 工单已经结束本轮，且没有悬而未决的问题。已订阅线程上的一个触发可以让它继续。

## 执行器

每个工单会得到一个名为 `worker-<ticket id>` 的执行器 Session，以及一个以该工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以运营者的操作系统用户身份运行命令，无需审批。它的 `dsh-superagent-worker` 预设包含工作所需的工具，并会在 5 秒后把前台 shell 命令转为后台任务。这样 worker 就能在下一步接收新消息，而不必等一条耗时命令跑完。

主 Session 使用 `dsh-superagent-router`，同样有 5 秒的 shell 与任务等待限制，但工具集更小，只用于路由。会话会保留创建时选定的预设。worker 的子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与 worker 槽位

当一轮结束时仍有 shell 任务或子智能体在运行，工单会保住它的 worker 槽位并保持"执行中"。它不会被报告为等待，主 Session 也收不到等待报告。某个任务或子智能体完成时，会在同一槽位里带着结果唤醒执行器。一旦某轮结束时没有后台工作，执行器就会正常报告"等待"。

每轮结束后，后台工作最多有 30 分钟完成时间。到达该上限时，shell 任务会被杀掉，工单被报告为等待中。报告包含执行器最后的说明，以及哪些任务被杀掉、哪些子智能体仍在活动。子智能体允许继续运行。执行器会在下一轮读取被终止任务的结果。

交接给人会立刻释放槽位，并让报告继续有效。这适用于 `ready` 报告或提问之后（除非此后又有输入到达），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时，子智能体停止。shell 任务（例如供人评审而起的服务器）可以继续运行，直到派工结束。它们不占槽位，也不受 30 分钟上限约束，包括在后续轮次之后。它们的完成不会唤醒执行器；执行器会在下一轮读取结果。

人也可以直接在执行器 Session 中写入来启动一轮。它的后台工作遵循同样的规则。

派工结束时，它的 shell 任务会被杀掉，且不唤醒会话。它的子智能体被释放，它们唤醒的任何完成轮次都会被丢弃。替代的派工及其等待中的输入，会在该关闭过程完成之后启动。

在 DeepSeek Harness 进程内停止或重启插件，走的是同一条关闭路径。尚未进入会话历史的输入会被保留。关闭时对每个 worker 的后台工作最多等待 10 秒；进程重启则直接结束这些工作。忙碌中被中断的派工，会带着一条恢复说明重新启动。

worker 的子智能体（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预设，并继承 worker 的权限。它们只保留 worker 允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令 60 秒后转入后台。子智能体结束时，它的任务会被杀掉。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，prepare 命令会在执行根目录下以 `sh` 运行一次。它有十分钟完成时间。若没有 prepare 命令，worker 会在一个空目录中启动。

命令失败会导致工单失败，并记录其输出。重试，或人在该工单某个线程上发消息，会再次尝试准备。典型的命令会用 `git worktree` 创建一个检出。当一个 pull request 分支路径的最后一段与该工单的短名匹配时，该 pull request 归属于这个工单。

### 并发

工单从一次启动开始时（含准备阶段）就占用一个 worker 槽位；对于唤醒空闲执行器的那种投递，则从投递时开始占用。它在整个活跃轮次中也一直占用该槽位。

配置的并发上限作用于这些槽位，另有一个额外槽位，专供人的消息或状态查询使用。当常规槽位已满时，这类唤醒可以使用额外槽位；而在新启动之前，它会先占用下一个空出的槽位。因此新工作无法阻止人继续某个既有工单。

其他输入（例如 CI 结果）要等常规槽位。启动会在 `working / queued` 中等待槽位空出。各次启动是并发执行的，因此一条缓慢的 prepare 命令只会拖慢它自己的工单。

### 执行变量

prepare 命令与执行器指令会收到同一组执行变量。命令读取环境变量；执行器在其提示词中读取这些变量的值与描述。其中都不包含凭据。

| 变量 | 由谁注册 | 取值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 发起该工单的 Issue 或 pull request；若是 pull request，还包括它的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及发起该工单的群 |

工单专属的取值来自它的目录和发起它的那个触发。其他取值来自当前的部署设置。只有面板可以修改执行环境设置；发给主 Session 的文本无法改变已配置的 shell 命令。

worker 通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被禁用的命令在按名称调用时会失败。

这些封装与目录只是建立默认值，并不构成安全边界。worker 仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词控制。宿主不含任何合并专用的判断逻辑。

默认情况下，执行器绝不以智能体账号启用自动合并：GitHub 会把合并归给启用它的人。交付要求必须指定另一个账号的 CLI 来执行合并。若没有指定，就由人来合并该 pull request。

默认指令只允许对"为该工单开启的 pull request"启用自动合并，条件是：它已就绪、所需批准覆盖了 head commit，且新增与删除合计少于 200 行。在推送另一版修订之前，执行器会撤回自动合并。

不含正文的评审（例如批准）也会作为触发到达，并能唤醒正在等待评审的执行器。这些指令约束的是智能体，而不是 GitHub 的合并规则。要强制要求批准，就在分支保护里设为必填，并开启"驳回过期批准"。想改为必须人工合并，就省略合并用的 CLI，或删掉自动合并那一段。

## 工单如何结束

- **就绪但没有 pull request：** 一份 `ready` 报告会把工单以"已完成"结束。
- **无事可做：** 若执行器发现没有需要人处理的工作，例如请求无法复现或已被取代，它会报告 `dropped`。工单在无消息的情况下结束——除非命中的某条规则要求发一条——而人之后在其线程上发的消息会恢复它。

### Pull request

一旦执行器报告了工单起步时所在的 pull request，工单就开始跟随它。它也会跟随每个从它的分支开出、且已被执行器报告或被 GitHub 来源发现的 pull request。被重新打开的 pull request 会再次被跟随。

当该工单开启的所有 pull request 都不再处于开启状态时，工单即告完成。如果它没有开启任何 pull request，那么它跟随的所有 pull request 都必须已关闭。此时它以最后一次相关关闭的结果结束，并保留它的订阅，以便之后的人类评论恢复它。

当被恢复、重试或恢复执行的工作尚未完成时，一次关闭不会结束工单。同样，如果执行器确认或回复了一条它拥有的后续发言，但此后既没有给出非 `progress` 的报告、也没有在读到该消息后结束一轮，关闭同样会等待。之后的 `ready` 报告会在同一条 pull request 完成规则得到满足时结束工单。

聊天渠道会收到一条关于 pull request 结果的最终通知。GitHub 本身已经在 pull request 上展示了结果。移除工单对某个 pull request 的订阅，也会让它停止跟随那个 pull request。

因此，"等待评审"意味着：有一份 `ready` 报告，并且有一个 pull request。

### 后续发言与上下文线程

执行器会判断其工单自有线程上的人类后续发言。它处理范围内的请求，并把超出范围或属于其他工单的请求交还回去。一旦没有执行器拥有该消息，它就成为一个送往主 Session 的候选。除此之外，主 Session 只能按当事人的请求停止工作，而不能对后续发言另作处理。

一条输入在被会话带入某个步骤，并且随后产生报告或结束一轮之后，才算被读取。工单结束时，未被读取、也未被确认、回复或交还的消息会回到评估，具体见 [002 授权](002-authorization-zh.md)。已被读取却未处理的消息（例如一句感谢）不会回去。

仅作上下文跟随的线程仍会投递消息，但不会让工单拥有人类后续发言的归属权，也不会恢复已结束的工单。这些消息可以被独立研判。

当有活跃工单订阅时，来源会轮询已订阅的线程；在最后一次触发与该订阅工单结束两者中较晚者之后，还会再持续两周。此后，消息只能通过常规入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、出错（记为 `failed`）时，工单不接受任何自动输入。

模型服务商或网络的一次性失败——HTTP 408、429 或 5xx，以及被拒绝、被重置或超时的连接——会先重试，共三次，退避时间递增：启动会重跑一次；某一轮失败的 worker 会被告知继续；失败的 prepare 命令不重试。

一旦失败，CI 与机器人消息仍会被记录在它上面，但不会投递，也不会唤醒会话。

它的工具仍然可用，因此人可以直接在会话里继续。

启动失败不会自行重试。

人的消息、之后一份既非 `blocked` 也非 `failed` 的报告，或一次重试，都会解除这一挂起状态。

该状态由已存储的报告与输入推算得出，因此重启后仍然保持。

### 重试

当开启中的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新建一次派工——它会重新启动 worker，并接收等待中的输入——就是这三种情形的解决办法。

一旦人的消息抵达了受阻或失败的工单，执行器就拥有了该消息，于是工单显示为执行中，或在该失败的启动重新开始时显示为已排队，并且不再提供重试——除非那条消息的投递本身失败了。

重试会结束当前派工，并在同一个执行器 Session、同一个目录、分支和 pull request 上启动新的派工。

执行器模型只在创建 Session 时生效；已存在的 Session 会保留它原来的模型。

### 重启

运行中的派工会以"宿主已重启"结束，新的派工则带着一条恢复说明启动，提示执行器在重复任何外部操作之前，先检查自己的目录、git 历史和 GitHub。顺序上最旧的工单优先。

处于等待、就绪、受阻或失败状态的派工保持不变——除非在该报告之后又有输入抵达，那样它们也会重新启动。

会话、目录、订阅、待处理消息以及下文所述的已存储工作，在重启后都会保留；"每个执行器 Session 把哪些消息带入了自己的历史"这份记录同样保留。一个步骤在认领消息之后、调用模型之前就会做这件事：被重启打断的那一轮取走的消息，只要之后有报告或一轮结束，就算已读；而某个步骤已经认领、却在进入历史之前被取消或出错打断的消息，算作未读。

重试或重启会让新的派工再次收到那些：投递给它所替代的那个派工、但执行器 Session 并未取走的消息——取消或被中断的步骤可能把它们丢掉了。如果会话里还留有一份副本在等待（由重启保留，或在崩溃后持久化），它会在新派工的第一条消息之前被取出，从而新的投递是唯一的副本。

### 已存储的工作

dsh-superagent 在做出决定之后要做的事——例如把候选、后续发言或报告转达给主 Session，启动一次派工，或投递一条输入——会先被存储，然后再执行。

转达或投递失败时（例如无法联系到其会话），会在 2 秒后重试，之后延迟翻倍直至一分钟；启动失败则会让工单失败，除非那是上文所说的一次性失败。

每一类工作，只有在连续三项失败之后，才会在总览的"系统问题"中报告错误；投递输入失败则改为显示在它对应的工单上。

发往主 Session 的转达与通知都保持原有顺序；某一项失败会挡住同类中后续的项。

### 来源失败

GitHub 来源会分别读取每个 Issue、pull request 和线程：读取失败时，错误保留在该线程上，下次轮询会重新读取，并计入来源的错误数——默认连续三次轮询失败后才会报告来源错误；任何一次成功的轮询都会重置计数。

当智能体失去对某个私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会被重试。

一个已被通知的 Issue 或 pull request，如果持续读取失败，会在首次读取失败的一天之后被丢弃；如果 GitHub 报告它已被删除，则立即丢弃。此后它不再导致轮询失败，其线程保留错误，而来源的状态会列出它。

来源的读取位置停留在原处，因此之后的通知或对该线程的轮询会补读失败期间遗漏的内容。

飞书事件消费端会报告每一次失败，而对已订阅话题的轮询会把各自的失败保留在对应线程上。

GitHub 列表或飞书页面中格式异常的条目会被跳过，并由来源状态计入统计。

### 渠道失败

外发消息像已存储的工作一样被存储并发送，退避重试从 5 秒开始，翻倍直至 300 秒。

工单发往同一个会话的消息，按入队顺序发出，因此它的确认会先于之后的回答或结果：若该工单先前有一条发往同一会话的消息尚未发出，后续消息就会等待，直到那条消息连续失败三次并显示为问题才继续。

其他工单的消息，以及不属于任何工单的消息，都不必等它。

一条有过失败尝试的消息，在发出或被撤回之前，都算作一个系统问题。

只有当来源已不再监听该会话，或来源回应称该会话永远无法接收它时，消息才会被丢弃；来源关闭期间，消息会等待。

在 GitHub 上，这对应已删除的 Issue 或已锁定的会话；在飞书上，对应被撤回的消息或飞书已找不到的消息。

对一条已不存在的评审评论的回复，会改为发往该 pull request 的会话。

被丢弃的消息保留其记录，包括丢弃的时间、原因以及它原本属于哪个工单，因此它绝不会被重新入队；被丢弃的确认会显示为"已丢弃"，而不是"已发送"。

### 暂停处理

会停止派发、新的评估、评估超时、输入投递和回复；已经开始的启动会等到处理恢复后再继续。

来源继续记录触发，正在运行的一轮执行器也不会被中断。

人对已结束工单发的消息会等待：暂停后的第一次处理会恢复该工单——前提是它的授权按当时的策略仍然成立。

进行中的评估在暂停期间不会过期；它的截止时间会按暂停时长相应推后。

### 无效配置

某个来源的配置被它的"种类"拒收时，该来源实例会被禁用。
